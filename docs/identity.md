# Identity, permissions and the two doors

How this app decides who you are, what it lets you do, and what it refuses to decide for itself.

Read this before changing anything in `internal/qtsauth`, `internal/idmap`, `internal/guard` or `internal/breakglass`, and
before believing any claim about what an administrator can do here. The authority for the design is
[PLAN.md](../PLAN.md) decisions 3, 4, 5, 6, 7 and 12 and [docs/design/m4-contract.md](design/m4-contract.md); this
document is the readable form of them.

## The short version

- There is no login of our own on the normal path. You are whoever QTS says you are.
- Every file operation runs in a separate process that has already dropped to your uid and your groups. The Linux kernel
  decides what you may touch; this app only predicts, to grey out buttons.
- An administrator's operations run as root, exactly as File Station's do. Root is not a bypass of the safety rules: the
  guard, read-only mode and the confirmation ladder all still apply.
- There is a second door — a local password on its own TLS port — for the case where QTS itself is broken. It is an
  emergency door, it is loud in the audit log, and everything created through it is owned by `root:root`.

## 1. The two doors, and that they never mix

| | Main listener | Break-glass listener |
|---|---|---|
| Address | `127.0.0.1:8770` (loopback only) | `0.0.0.0:8771`, TLS only |
| Reached through | the QTS Apache reverse proxy at `/qnapfilemanager/` | directly, `https://<nas>:8771/` |
| Who it authenticates | the QTS desktop session (cookies), nothing else | one local bcrypt account, nothing else |
| Session cookie | `qfm_sid`, `Path=<proxyPrefix>/`, `SameSite=Lax`, `HttpOnly` | `__Host-qfm_bg`, `Path=/`, `Secure`, `SameSite=Strict`, `HttpOnly` |
| Identity of the worker | your uid (admin → root) | root |
| Content it creates is owned by | you (see §7) | `root:root` |
| Certificate | none of ours — QTS's | self-signed, generated by us (§8) |

The two never mix, and that is the whole security argument for having a second listener:

- A `qfm_sid` cookie presented on 8771 is ignored; a `__Host-qfm_bg` cookie presented on 8770 is ignored.
- `qtsauth` is never consulted on the break-glass listener, and the local password hash is never consulted on the main one.
- `/api/breakglass/login` does not exist on the main listener at all.
- The two listeners use **separate session stores** — separate maps, separate mutexes, separate CSRF tokens — not one
  store with a flag, because one forgotten comparison in a shared store would let a QTS cookie redeem a break-glass session.

What is *identical* below the door: the same mux, the same routes, the same guard, the same `readOnly` switch, the same
confirmation ladder, the same audit log, the same worker pool. The listener decides only **who you are**, never **what you
may do**. There is exactly one API surface, because a second route table would be a second place to forget a check.

`web.breakGlass.enabled = false` makes the second door inert with no code change, and the daemon is then loopback-only.

## 2. How a QTS session becomes an identity

The app is served from the QTS origin through App Center's reverse proxy, so QTS's own cookies arrive first-party.

1. The QTS desktop holds `NAS_USER` (the username) and either `qtoken` (QTS 5) or `NAS_SID` (older firmware).
2. The browser asks the app for `api/session`; the cookies come along.
3. The app validates them against QTS itself, on loopback:
   `GET http://127.0.0.1:<port>/cgi-bin/authLogin.cgi?qtoken=<t>&user=<NAS_USER>` (or `?sid=<s>`). The port comes from
   `/etc/config/uLinux.conf`, falling back to 8080. It is **never** derived from the incoming request's host — a
   request-derived host is an attacker-supplied validation server.
   On a unit with "Force secure connection (HTTPS)" on, port 8080 answers `302` rather than XML; the call then retries over
   HTTPS on loopback, taking the port from the redirect's `Location` (port only, host forced back to `127.0.0.1`) or from
   `[Stunnel] Port` in `uLinux.conf`. QTS's self-signed certificate is accepted there because the connection never leaves
   the machine.
4. The XML answer is parsed leniently for `authPassed`, `isAdmin`, `authSid` and `username`.
5. On success the app resolves the username to a Linux identity (§3), decides admin-or-not (§4), and issues **its own**
   session cookie bound to a hash of the QTS token.

**Caching and revalidation.** A validated cookie pair is cached for **60 seconds**, with single-flight so a burst of
requests produces one call to QTS rather than a hundred. The cache is a latency optimisation, never an authority
extension: **before any write the session is revalidated unconditionally**, cache or no cache. If QTS says the token is
gone — the user signed out of the desktop, or the token rotated — our session is destroyed in place and the UI swaps to a
re-authentication panel rather than a top-level redirect (a redirect inside the desktop's iframe would take over the whole
desktop). That coupling is what makes "no separate login" honest instead of a second, longer-lived credential.

**When the cookies do not arrive at all** (a bookmark to the wrong host, a browser blocking the cookie, a broken
desktop), the main listener has nothing else to try: it says so and offers no form. The remaining way in is the
break-glass door on its own listener (§8). **There are two doors in 1.0 and no third.**

The design plan's `identity-and-hero-plan` §5.3 describes a middle door — a credential-proxy form posting to
`authLogin.cgi?user=&pwd=` — between those two. **It was not built in 1.0**; the supporting call exists in
`internal/qtsauth` but no route reaches it. It is deferred, and listed under `Unreleased` in
[CHANGELOG.md](../CHANGELOG.md).

## 3. From a username to a Linux identity

`internal/idmap` reads `/etc/passwd` and `/etc/group` in pure Go, reloading when either file's mtime or size changes. The
primary gid is always included in the group set — it is not listed in `/etc/group` and forgetting it is the classic way to
compute the wrong permissions.

**Domain users** (LDAP or AD) are not in `/etc/passwd`. They are resolved once per session with a bounded exec of
`id -u` / `id -g` / `id -G` (or `getent`), and the answer is cached for the life of the session.

- If `id -G` is unavailable, the session is admitted with an incomplete group set and the UI shows a **"groups incomplete"**
  banner (`groupsIncomplete` in `api/session`). Permission *hints* may then be wrong; the kernel is still right, so
  operations behave correctly even when the greyed-out state does not predict them.
- If **no uid resolves at all, the session is refused**. It never falls back to root, never falls back to `nobody`, and
  never guesses.

## 4. Fail-closed rules

Each of these exists because the failure it prevents is worse than the inconvenience it causes.

| Situation | What happens | Why |
|---|---|---|
| `authPassed` is not 1, or the response cannot be parsed | no session | the only evidence of identity failed |
| The `sid` path is used and the validation response does **not** carry a username | the `sid` door is disabled | otherwise `NAS_USER` is an unauthenticated claim and could be set to somebody else's name |
| `isAdmin` is absent from the response | a **normal-user** session | an administrator can re-enter their password once; silently promoting is not recoverable |
| `isAdmin` says admin but the local identity is neither uid 0 nor in `administrators` | the **lower** privilege wins, and the disagreement is logged | two sources disagreeing about privilege is itself an event worth seeing |
| No uid resolves for the username | the session is refused | §3 |
| QTS is unreachable on loopback | `503 qts_unavailable` and a banner — never an anonymous session | an outage must not become an authentication bypass |
| The config file cannot be read while reconciling the read-only switch | the guard is forced to **read-only** | PLAN §2.6: not knowing the persisted state means refusing writes |
| No break-glass password is configured | port 8771 **does not bind** | an open port that can never authenticate is pure attack surface |

## 5. What an administrator can and cannot do

An administrator's session is served by a worker running as **uid 0** (PLAN decision 6, the File Station parity choice).
All administrator sessions share one `root` worker. There is no separate "arm root mode" step; the safety rails are what
make a dangerous operation deliberate.

**Can:** see and traverse the whole filesystem, including `/`, `/etc`, `/root`, `/mnt/HDA_ROOT` and the `.qpkg` trees;
change ownership; change the mode of files they do not own; turn read-only mode off in Settings.

**Cannot:**

- Skip the guard. Protected and warn-class paths demand a confirmation token exactly as they do for anybody else.
- Write anything while `readOnly` is on. The switch is global, persisted, and defaults to **on** at first install.
- Delete or rename `/` or any first-level system directory (`/bin`, `/etc`, `/lib`, `/sbin`, `/usr`, `/var`, `/home`,
  `/root`, `/opt`, `/mnt`, `/share`, `/dev`, `/proc`, `/sys`). Those are denials, not confirmations.
- Read or write the app's own `config/` or `logs/` directories through the app — the password hash and the audit trail are
  not browsable from the thing they are auditing.
- Change the break-glass password over HTTP. There is no such route, admin-only or otherwise (§8).
- Descend into `.zfs`, or write inside `/proc` and `/sys`, regardless of mode bits.

An administrator with SSH can of course do all of this anyway; the guard is there so that a mis-click in a file manager is
not the same act as a deliberate command typed as root.

## 6. The root worker, and why the front end is not it

The root front-end process never touches user data. It re-execs its own binary in `-worker` mode with
`SysProcAttr.Credential{Uid, Gid, Groups}` — groups explicit, never nil — and talks to it over an inherited anonymous
socketpair with length-framed JSON. Listing, stat, search, copy, delete, trash and upload temp files all happen **inside
the worker**, as you.

Downloads and uploads go the safe way round: the worker opens the file as you, so the kernel performs the permission check
at `open`, and passes the descriptor up with `SCM_RIGHTS`; the front end only moves bytes through a descriptor it was
handed. Never the reverse — the front end never opens a file on the worker's behalf.

This is **INV-1**, and a test enforces it: `internal/web` must not import `internal/fsops`. The one sanctioned exception is
the front end creating the `.@qfm_trash` directory at a volume root (PLAN decision 10), which is audited, disclosed in the
Trash panel, and hardened as PLAN §2.7 describes.

In-process `setuid`/`setresuid` is rejected outright: a Go runtime with live threads cannot drop privilege reliably, and a
process that is "mostly" not root is worse than one that is honestly root.

## 7. Who owns what an administrator creates

An administrator's worker is root, so without a rule everything an administrator made would be `root:root` — a support
folder full of files the real user cannot then delete. So:

**The rule.** When an administrator creates content in an ordinary location, the worker chowns the new inode to the
**real signed-in QTS user** (`wproto.CreateAs`), matching File Station. It applies to new folders, uploads and copies.

The details that matter:

- **Chown only, never chmod.** `GID` travels as `-1`, so a setgid parent keeps the group it was going to give
  (`administrators`, typically) and inherited ACLs are left alone. An `fchmod` here could widen a POSIX ACL mask or, on a
  hero dataset with `aclmode=discard`, silently drop the inherited ACL.
- **Ordinary locations only.** Both spellings of the parent — the requested path and the resolved one — must classify as
  `normal`. A guard-warn or protected parent (`/etc/config`, the install tree, a mount root, `/proc`) is a genuine system
  location, and content created there stays root-owned.
- **A move preserves the source's owner and group** when the worker is root — that is what a rename would have done, so
  that is what a copy-and-delete across filesystems does too. `As` is not applied to a move.
- **Chown is the exception, because chown *is* the ownership operation.** The permissions routes never send `As`; asking
  for an owner and silently getting a different one would be the worst possible behaviour in the one dialog that is about
  ownership.
- **A non-administrator's worker is already running as that user**, so everything it creates is theirs by construction and
  no chown is requested (and a non-root chown to another uid is `EPERM` anyway).
- If the create succeeds but the chown fails, that is reported honestly as `owner_unset` — "the folder was created but
  could not be assigned to you" — rather than as a bare refusal that a retry would turn into "already exists". The folder
  is not rolled back.

**The break-glass exception.** A break-glass session is an administrator session, but it is **not a QTS user** — there is
no real person behind it to own anything. So `CreateAs` is empty and everything it creates is **`root:root`**. The UI says
so in a banner that cannot be dismissed, and the audit line says so too. This is the most likely lasting damage that door
can do, which is why it is stated in three places.

## 8. The break-glass door: what it is, and what it is not

**It is** a local administrator account on a second TLS listener, for the case where App Center or QTS's Apache is broken
and the normal door therefore does not exist. It must not depend on the thing it may have to repair.

**It is not** a convenience login, a second way in for daily use, or a way to act as a named user. It has no route that
can set, change, reset or reveal its own password.

How it is set up, and the properties that follow:

- The password is set **only** from the NAS shell, as root:
  `qnapfilemanager break-glass set-password` (with `disable`, `status` and `cert [-regenerate]` alongside). It refuses to
  run when it is not uid 0, when the config file is not owned by root, or when the config file is group- or
  world-readable. Minimum 12 characters, no composition rules; bcrypt cost 11 by default.
- **No password configured means the listener does not bind.** There is no unauthenticated bootstrap window over HTTP, in
  any form, ever.
- **Setting the password is the whole of the setup.** `set-password` generates the certificate too if there is not one
  yet, so `break-glass status` prints a fingerprint immediately; and the daemon re-reads the credential rather than
  caching it (guarded by an mtime+size check), so a password set from the shell takes effect on the next attempt **and
  brings the listener up** without restarting the app you are in the middle of repairing.
- **Changing or clearing the password destroys every live break-glass session**, via the `auth.local.updated` stamp each
  session carries. That is what makes `break-glass disable` an eviction rather than a suggestion.
- **A break-glass session is pinned to the address it was issued to**: the cookie presented from any other peer is
  unauthenticated, audited as a sessionless denial, and leaves the real session untouched. Cookies are host-scoped rather
  than port-scoped — the `__Host-` prefix does not change that — so without the pin every browser-trusted HTTPS service
  on the NAS hostname would receive a cookie redeeming a root session, and `api/session` would hand it the CSRF token.
- The certificate is self-signed, **never transmitted**, and generated on the NAS when the password is set or when the
  listener first binds — whichever happens first. Its SHA-256 fingerprint is printed to the app log at every start and by
  `break-glass status`. Compare it before you type a password into a page your browser has warned about —
  [docs/qnap-install.md](qnap-install.md) puts that comparison in the numbered procedure.
- Rate limits, all confined to this listener: 10 attempts per minute per source IP; 5 consecutive failures lock the
  account for 60 s, doubling to a 1800 s cap; and one bcrypt verification at a time with a queue of 4.
- **What the 400 ms failure floor does and does not hide.** Every failed attempt returns the same `401 auth_failed` body
  after the same minimum 400 ms, so "wrong password" and "no password is configured" are not distinguishable — which is
  the pair that matters, because the second would otherwise tell an attacker the door is unarmed. A **lockout is not
  hidden**: it answers `429 locked_out` with a `Retry-After`, and says so on purpose. Concealing it would leave the
  operator this door exists for hammering a door that will not open for up to half an hour, and `Retry-After` is the only
  thing that tells them to stop and wait.

Config keys (defaults in brackets): `web.breakGlass.enabled` [`true`], `web.breakGlass.addr` [`0.0.0.0:8771`],
`web.breakGlass.certFile` / `.keyFile` [beside the config], `auth.local.hash` [empty], `auth.local.cost` [`11`],
`auth.local.updated` [empty]. `auth.mode` stays `qts` for v1.0; `local` and `both` are refused outside `-dev`, because the
local account now has its own listener rather than a second form on the main one.

## 9. The guard: protected paths and the confirmation ladder

The guard is a **data table**, not scattered behaviour: `internal/guard/rules.go` is a list of prefix rules and
`guard.Check` / `guard.Classify` walk it. It runs in the root front end, before the RPC, and it applies to non-root
sessions too as defence in depth.

| Region | Rule |
|---|---|
| `/` and every first-level system directory (`/bin`, `/etc`, `/lib`, `/lib64`, `/sbin`, `/usr`, `/var`, `/home`, `/root`, `/opt`, `/mnt`, `/share`, `/dev`, `/proc`, `/sys`) | delete and rename **denied**, exactly (their children are unaffected) |
| `/dev` and below | write, delete and rename **denied**; chmod and chown **warn** |
| `/etc/config` and `/mnt/HDA_ROOT/.config` | every write **warns** (editing firmware configuration is a legitimate reason to use this app); deleting the directory itself is **denied** |
| `/share` when it is the QTS RAM disk | creating anything directly there is **denied** (it is lost on reboot) |
| The app's own install directory | every write **denied** |
| The app's `config/` and `logs/` | write, **read and even traverse denied** — the password hash and the audit trail |
| `.zfs` at any depth, and inside `/proc` and `/sys` | never descended into, never written — a component rule, because `.zfs` appears at any depth |
| Mount-point roots (`CACHEDEV1_DATA`, `ZFS530_DATA`, legacy `HDA_DATA`…) | checked dynamically, not by a static prefix; deleting one is level 2 |

A mutation is checked against **both** the requested spelling and the resolved (symlink-followed) one, and the stricter
verdict wins; the operation is then dispatched using the resolved canonical path. Reads check the requested spelling only,
which is a deliberate, documented residual (PLAN §2.5).

**The confirmation ladder** (`ui-ux` §4.2, as the confirm envelope carries it):

| Level | What triggers it | What you see |
|---|---|---|
| **L0** none | navigate, read, download, copy to clipboard; new folder or rename inside an ordinary share | a toast, with Undo where Trash makes one possible |
| **L1** simple confirm | move to Trash; overwrite on conflict; a cross-device move; more than 100 items in one operation | a confirmation dialog, grade 1 |
| **L2** typed phrase | permanent delete; **any** write under a protected path; a recursive chmod/chown over more than 500 items or touching a protected path; emptying Trash; deleting a mount-point root; more than 1 GiB or 1000 items | a danger-styled dialog with a phrase to type, grade 2 |
| **L3** impossible | the denials in the table above | the control is disabled with a reason, and the server answers 403 |

A confirmation is not a checkbox on the client: the server issues an **HMAC token** carrying a real scan summary (counts,
bytes, what the walk actually found), and the token must be redeemed with the operation. A client that skips the dialog
does not skip the token. Every delete requires a redeemed token regardless of size.

**Read-only mode** sits above all of it: one middleware rejects every non-GET API route with `403 read_only`, so a newly
added endpoint is safe by default. It defaults to **on** at first install. Turning it off requires an administrator
session, CSRF, an Origin check, an explicit client confirmation, and writes a forced milestone audit line. There is no
password on that toggle — the 2026-09-10 deviation to PLAN decision 7 — because under the QTS-session identity model this
app holds no password of its own to re-challenge against.

## 10. How a request is attributed to a person

Three independent locks on every non-GET request, because any one of them can be weakened by a browser change:

1. **A required `X-QFM-CSRF` header**, bound to the session. A cross-site `<form>` cannot set a header at all; a
   cross-site `fetch` that sets one triggers a preflight this server never answers.
2. **`Origin`/`Referer` host must equal `r.Host`** when either header is present, and a `Sec-Fetch-Site: cross-site`
   request is rejected outright.
3. **`SameSite`** on the session cookie: `Lax` on the main listener (it is legitimately framed by the QTS desktop) and
   `Strict` on the break-glass listener (it is never framed).

`Content-Type: application/json` alone could not have been the lock, because uploads are `application/octet-stream`.

The `__Host-` prefix on the break-glass cookie is not cosmetic: the browser refuses the cookie outright if anything ever
tries to set it with a `Domain` or a narrower `Path` — exactly the confusion a second listener on the same host invites.

Because the app sits behind a loopback proxy, `RemoteAddr` is `127.0.0.1` for every request on the main listener, so the
audit records `X-Forwarded-For` only when the peer really is loopback. On the break-glass listener there is no proxy, so a
forwarded header there would be a forgery and is not trusted: the real peer address is what is recorded.

## 11. The audit log and QuLog

The audit log is JSON lines, written by the root front end, at `<install>/logs/audit.jsonl` (rotated; `logging.audit`
overrides the location). Every operation is recorded in **two phases** — an `intent` line before anything is dispatched
and a `result` line after — so an operation that crashed halfway still left evidence that it was attempted. The log
directory is mode 0700 and is unreachable through the app itself.

Each event carries `Door`, stamped once at session creation, because the first question after an incident is *which door
did this come through*. In 1.0 it is `qts` or `local`; the `credential` value is defined for the deferred credential-proxy
form (§2) and is never written.

**Milestones** are mirrored to QuLog with `/sbin/log_tool`, so they appear in QuLog Center beside QTS's own events. QuLog
is never written per file. A milestone is: a sign-in; the read-only toggle; **any** denial (except a routine
`confirm_required` challenge, which is recorded but not mirrored); any chown; a large delete; any write under
`/etc/config`; and everything the break-glass door does — the listener binding, a certificate generation with its
fingerprint, every login **success and failure**, every lockout entered and left, session issue and destruction, and the
password's `updated` stamp changing under a live daemon.

Detail strings are bounded and **path-free** in the QuLog mirror: `door=local ip=192.168.1.40 cost=11`,
`lockout 5 failures, 60s`. The CLI subcommands write nothing to the audit log — they are a different process, and a second
writer to a single-writer file is a corrupted file. What they changed becomes visible, and audited, the moment the daemon
notices.

## 12. What the kernel decides, and what the app predicts (INV-2)

This is the invariant that most often surprises people reading the code, so it is stated plainly.

**The kernel decides.** Every permission question is answered by the Linux kernel, at the moment of the syscall, in a
process that is already running as you. `EACCES` and `EPERM` are treated as *truth*, not as bugs to work around. The app
does not re-implement POSIX mode bits, does not evaluate ACLs to decide whether to proceed, and does not compute
"effective permissions".

**The app predicts.** From your uid, gid and group set it computes *hints*: which toolbar buttons to grey out, what the
permissions grid should show as likely, whether a chmod is expected to be refused. A hint is a courtesy, and it can be
wrong — an ACL, a read-only mount, an immutable attribute, or a hero dataset's `aclmode` can grant or refuse where the
arithmetic says otherwise.

The consequences, all deliberate:

- A control whose only reason to be disabled is a **capability prediction** stays **enabled**, with an explanatory
  tooltip. Only certainties disable a control: read-only mode, an impossible selection, and a guard denial. Predicting a
  refusal and then blocking the attempt would mean the app, not the kernel, made the decision.
- After a chmod or chown the app **re-`lstat`s the inode** and diffs the result against what was asked. What it reports
  is what actually happened — "changed N of M, K owned by others" — not what should have happened. The kernel silently
  dropping a setgid bit for a non-member is a real thing, and it shows up in the diff.
- A recursive job treats a per-item `EPERM` as a **skip**, not a failure, and finishes with counts.
- An empty listing and a listing you are not allowed to read must never look the same. The refusal names the kernel's
  verdict: *"You do not have permission to list this folder. It is owned by `root` and its mode is 0750."*
- Permission-semantics tests are skipped on Windows and when not running as root, and the real behaviour is covered by
  the root and ZFS CI jobs. The alternative — simulating the kernel in a test — would test the simulation.

## 13. Known residuals

None of these were closed by M4, and a v1.0.0 tag does not imply otherwise. Each is stated in full in
[PLAN.md](../PLAN.md) with the reasoning for accepting it, and summarised in the `Security` sections of
[CHANGELOG.md](../CHANGELOG.md):

§2.0 the dispatch race between the front-end guard check and the worker's re-resolve; §2.4 the rename no-overwrite
fallback where `renameat2(RENAME_NOREPLACE)` is unavailable; §2.5 the read-side guard checking the requested spelling
only; §2.6 the audit result-write timeout under a wedged sink; §2.7 trash-root creation at an attacker-writable mount
root. Plus the M4 residuals: a root daemon answering on the LAN at all, the certificate being trust-on-first-use with no
revocation, the break-glass password living outside QTS's account policy, and lockout state being lost on restart.

Two more, stated here because they are the ones an operator meets in practice:

- **A lockout is announced, not hidden** (§8). `429 locked_out` with a `Retry-After` tells an attacker that an account
  exists and is currently locked. Accepted: there is exactly one account, so its existence is not a secret, and the
  alternative harms the operator far more than the attacker.
- **Two writers to `config.json`.** The daemon rewrites it when an administrator changes the read-only switch in the app,
  and the `break-glass` CLI rewrites it from the shell. They coordinate through a lock file with a two-second timeout, so
  neither can interleave with the other and neither can corrupt the file — but the two must not be run at the same
  moment: the CLI can fail with a lock timeout, and the settings save can be slowed by the wait. Run the CLI when nobody
  is changing settings, and re-run it if it times out.

## To verify on hardware

Marked here because CI cannot answer them:

- The exact cookie names and attributes inside the QTS desktop window (`NAS_USER`, `qtoken`, `NAS_SID`; `Secure`,
  `SameSite`, `Path`), and whether the desktop's iframe URL differs from the bare proxy path.
- Whether `authLogin.cgi` validation actually returns `username` (which gates the `sid` door) and `isAdmin` (which gates
  administrator status over SSO) on both firmware families, and whether repeated calls produce QuLog noise or rate limiting.
- Whether the QTS proxy sets `X-Forwarded-For` or any other client-attribution header. Without one, every peer on the main
  listener is loopback and the authentication failure budget can only key on the presented username — an accepted M0
  residual (PLAN "must verify" item 10).
- `id -G` and `getent` availability, the `admin` uid, and the exact name and gid of the `administrators` group.
- That 8771 is free and not blocked by QuFirewall, and that the listener does not bind before a password is set.
