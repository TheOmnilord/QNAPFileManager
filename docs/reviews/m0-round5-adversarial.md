1. **P2 — R4-A1/R4-S1 partial: effective throttling now creates a shared-proxy lockout.**  
   [auth_limits.go:144](C:/Dev/QNAPFileManager/internal/web/auth_limits.go:144) rejects every uncached validation once an IP accumulates twenty distinct failures. [security.go:47](C:/Dev/QNAPFileManager/internal/web/security.go:47) falls back to the loopback peer when `X-Forwarded-For` is absent or unusable. Consequently, on that QTS proxy configuration, one unauthenticated client can exhaust the bucket for **all users**. Repeating the burst after expiration sustains disruption. This collateral rejection is introduced by enforcing the previously ineffective budget.  
   **Minimal fix:** distinguish shared/unattributed proxy traffic, reserve bounded revalidation capacity for established sessions, and provide bounded recovery admission for new credentials; retain the upstream concurrency ceiling. Verify proxy-generated client-IP headers before treating them as individual-client buckets.

2. **P2 — R4-A2 partial overall: first-login followers still occupy execution slots.**  
   [session.go:192](C:/Dev/QNAPFileManager/internal/web/session.go:192) acquires web execution capacity before calling the verifier. Before a web session exists, eight concurrent requests presenting the same credential can therefore hold all eight slots: one performs slow QTS validation, while seven wait on the verifier’s single-flight channel at [verifier.go:183](C:/Dev/QNAPFileManager/internal/qtsauth/verifier.go:183). Other new logins and stale sessions queue behind them. The reported **existing-session** scenario is fixed: its followers acquire the session lock before execution admission and consume only waiting capacity. The corresponding first-login case remains.  
   **Minimal fix:** deduplicate credential authentication before acquiring execution capacity; count credential followers against the shared waiting limit, just like session followers.

3. **P2 — Additional pre-existing defect: listing still requires read permission on intermediate directories.**  
   [fsops.go:375](C:/Dev/QNAPFileManager/internal/fsops/fsops.go:375) opens the entire resolved directory path through `os.Root.OpenFile`. With `/outer` mode `0111` and `/outer/readable` mode `0755`, the kernel permits listing the latter, but `os.Root` opens intermediate directories read-only and rejects `/outer`. The new O_PATH helpers fix stat, readlink and downloads, but leave this browse operation inconsistent with INV-2. The new permission tests check refusal to list the search-only directory itself, not successful listing beneath it.  
   **Minimal fix:** open the resolved parent using `walkOPath`, then open the final directory with `O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC`; add the readable-child regression case.
